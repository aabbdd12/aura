AURA Developer Guide

Version 1.6 — Building Modules for AURA

1. AURA as a Platform

AURA is a protocol and a platform, not just a statistics tool. Its command interface draws inspiration in part from established statistical software such as Stata, but AURA is an independent platform — the protocol below, the internals, and the behaviour are its own, and it is not a clone of any single package. Its core value is the separation between three layers:

┌──────────────────────────────────────────┐
│  USER LAYER                              │
│  Types commands. Sees results.           │
│  No Python knowledge required.           │
├──────────────────────────────────────────┤
│  PLATFORM LAYER  (AURA core)             │
│  Parses input. Manages session state.    │
│  Routes commands. Stores results.        │
│  Refreshes GUI. Manages workspace.       │
├──────────────────────────────────────────┤
│  MODULE LAYER  (.auru files)             │
│  Pure Python. Full scientific stack.     │
│  Reads data. Computes. Returns output.   │
└──────────────────────────────────────────┘

What the platform provides to the developer

When you write a .auru module, AURA automatically handles:

  • Parsing — the user's raw command string is parsed into a structured object (parsed) with validated varlist, if/in conditions, options, and weights
  • Session state — the active dataset, all labels, all stored results (r/e/s), command history
  • Multi-dataset workspace — access to all loaded datasets by name or declared source id
  • Result storage — declare __aura_class__ and return a dict; AURA posts it to the right namespace automatically
  • GUI refresh — emit session.events.emit("data_updated") and all panels update instantly
  • Library availability — numpy, pandas, scipy, statsmodels, matplotlib are already imported in the process; your import statements are instant cache lookups

What the developer provides

  • A .auru file named after the command
  • A run(session, parsed) function
  • The statistical logic and output formatting

That is all. No registration, no configuration, no restart needed.

2. Module Architecture — The .auru Protocol

Every .auru module follows the same three-step contract:

┌─────────────────────────────────────────────────────────────────┐
│  1. DECLARATION   The developer declares the command's syntax   │
│                   via args(). AURA validates everything.        │
│                                                                 │
│  2. SILENCE RADIO Pure Python. Any library, any external tool.  │
│                   AURA does not look in, does not constrain.    │
│                                                                 │
│  3. RETURN        result() / text() / error() / warning()       │
│                   AURA collects what the module emits.          │
└─────────────────────────────────────────────────────────────────┘

Canonical module shape

"""mymod — One-line description."""
__aura_class__ = "rclass"     # or "eclass" / "sclass" / omit

import numpy as np   # any scientific library you want (no AURA imports needed)


def _compute(df, var, alpha):
    """Pure Python. Testable with pytest alone — no AURA dependency."""
    return {"stat": float(df[var].mean()), "n": int(df[var].notna().sum())}


def run(session, parsed):

    # 1. DECLARATION — args() is your only validation surface
    a = args(parsed, session,
        varlist = varlist(min=1, max=1, numeric=True),
        options = {
            "alpha": real(default=0.05, min=0, max=1),
            "level": integer(default=95, min=1, max=99),
        },
    )

    # 2. SILENCE RADIO — pure Python
    res = _compute(a.df, a.varlist[0], a.opt.alpha)

    # 3. RETURN
    return result(
        text = f"stat = {res['stat']:.4f}   N = {res['n']}",
        kind = "r",
        **res,
    )

That is the entire protocol. No registration, no decorators, no AURA imports. The helpers args, varlist, flag, integer, real, string, varname, choice, result, text, error, warning, note, active_df, sw_pair, sw_load, sw_resolve are injected automatically into every .auru namespace by the execution engine.

The stable public API is auru.connect. Even though you don't import it, that is the module surface the helpers come from. Sections 3-10 of this guide describe what args() and the helpers do under the hood; they are reference material, not alternative protocols. For new modules, only the form shown above is supported.

Where to put your .auru file

1. Built-in registered commands  (core/execution_engine.py — AURA team only)
2. %USERPROFILE%\AURA\modules\personal\   ← your own modules
3. %USERPROFILE%\AURA\modules\plus\<package>\
4. %USERPROFILE%\AURA\modules\base\
5. ./auru/                                ← project-shipped modules

The first match wins; place a module in personal/ to override a base one.

Existing modules in this repo

Some files in ./auru/ predate the v0.2 protocol and use older patterns (direct core.syntax imports, raw dict returns, ad-hoc error strings). Treat those as legacy — they may still execute, but they are not the template for new work. The two canonical examples are:

  • examples/modules/diff.auru — an example module for the sw protocol: args(sw=True), result(kind='e')
  • auru/histo.auru — varlist, an aura: block, result(kind='r')

Their .aurh files show the help format that pairs with the protocol.

3. The args() / syntax() System (reference)

Reference section. In your .auru file you call args() — it is already injected into the namespace and is the public name of this API. Internally args() calls core.syntax.syntax(), documented below for understanding how validation works. Always write args(...) in modules, not syntax(...) or direct core.syntax imports.

args() is AURA's standardised input validation layer — analogous to a syntax-style validator in other statistical packages. It parses, validates, and type-converts all inputs in one call.

Import

from core.syntax import syntax, flag, integer, real, string, varname, varlist, choice

Calling syntax()

syn = syntax(parsed, session,
    varlist_spec = varlist(min=1, numeric=True),
    if_in        = True,
    weights      = ["aweight", "pweight"],
    options = {
        "detail"    : flag(),
        "level"     : integer(95, min=1, max=99),
        "cluster"   : varname(),
        "vce"       : choice("ols", "robust", "cluster"),
        "alpha"     : real(0.05, min=0.0, max=1.0),
        "noconstant": flag(),
        "title"     : string(""),
    }
)

Accessing results

syn.varlist        # list[str]  — validated variable list
syn.depvar         # str        — first variable (dependent)
syn.indepvars      # list[str]  — variables[1:] (regressors)
syn.df             # DataFrame  — data with if/in applied
syn.if_cond        # str|None   — raw if condition
syn.obs_range      # tuple|None — (1, 100)
syn.weight         # str|None   — weight variable name
syn.weight_type    # str|None   — "aweight"|"pweight"|...
syn.opt.detail     # bool
syn.opt.level      # int
syn.opt.cluster    # str|None
syn.opt.vce        # str
syn.opt.alpha      # float
syn.opt.title      # str

Option type functions

varlist constraints

varlist(min=0)                 # optional

Names and free text

A command whose words are not variables declares them instead of a varlist. The declarations go in args(), and are available in a module without an import.

a = args(parsed, session, namelist=namelist(min=2, max=3, id="thing"))
a.namelist                 # ["a", "b"]: valid names, which need not exist

a = args(parsed, session, namelist=name(name="who", id="person"))
a.who                      # "ann": one name, a string

a = args(parsed, session, anything=anything(name="e", id="expression"))
a.e                        # "a + b": the words as they were typed
Declaration Arguments
namelist() min=1, max=None, name= (the attribute; namelist by default), id= (the word in messages), local=False (names of local macros: a digit may come first)
name() required=True, name= (name by default), id=, local=False
anything() required=True, name= (anything by default), id=, equalok=False (a lone = is allowed), everything=False (if, in and using belong to the text)

Nothing given when something is needed is r(100) (id required); too few r(102); too many r(103); a word that cannot be a name r(198); a lone = r(101).

anything() stops at if, in, using, a [weight] or the comma, and x[1] stays in the text. With everything=True it stops at the comma only, and the module writes at its top level, so that AURA does not read those words as an if and an in before it runs:

__aura_free_text__ = True

Handing a value back — aura.local()

A module has its own local macros, which end with it. aura.local() reads and writes those of the command that called it, so a module can give a script a value:

aura.local("answer", 42)        # `answer' is 42 in the script that ran the module
caller = aura.local("mine")     # a local of that script ("" if it has none)

In a py: block of a script, the same calls act on the script's own locals.

What syntax() validates automatically

  • Varlist count (min/max), variable existence, numeric/string type
  • Option type coercion, bounds checking, valid choice values
  • Unknown option names (raises SyntaxError with clear message)

Abbreviation matching is automatic: , det → detail, , lev(90) → level.

if / in without syntax()

AURA evaluates the if / in written with a command once, on the whole dataset, before run() is called (core.qualifiers.mark_sample): a mistake in the condition stops there, and _n / _N in it are those of the whole dataset. The module receives the selected rows as parsed.sample, a boolean Series on the dataset's index (None without if / in), and applies them — df[parsed.sample] to compute on them, or, for a command that writes, its values on those rows only. syn.df and parsed.work_df(session) already hold them; core.qualifiers.select(df, parsed.if_cond, parsed.obs_range, session) reuses the same evaluation for the dataset's rows.

Which of AURA's own commands take if / in is declared in core.qualifiers.TAKES_IFIN (TAKES_IN_ONLY for in alone); any other command of AURA refuses them with r(101). A module from outside AURA (a package, your own module, a generated one) is checked after it ran: given if / in, it must have read them (parsed.sample, parsed.if_cond, work_df, syntax()), or its results are replaced by an error — never a result computed on every row.

Under the by prefix (commands/by_prefix.py), a command that takes if is run once per group, and parsed.sample is that group's rows (its if evaluated on the group, _n / _N counted in it). A module that applies parsed.sample — or select / row_mask with the session — therefore works by group with nothing more to write; one that re-evaluates parsed.if_cond by itself would compute on the whole dataset (for a group written without if, if_cond is a marker, core.qualifiers.BY_GROUP, that fails if evaluated).

The conditions a module uses inside its computations are its own: an option such as subpop() or cond1() goes through core.qualifiers.cond_array(df, text, session), a numpy boolean array (None when the option is empty), and a command the module runs (aura: block) reads its own if / in at its own level.

Do not evaluate a condition with df.eval / df.query. Every AURA command follows one rule, and pandas knows none of it: a condition whose result is missing leaves the observation out (if x != 0 does not select a row where x is missing), a numeric variable alone is true where it is non-zero (if urban), in a/b counts the whole dataset before any if, and a condition may use missing(), x == ., !, AURA's functions and the session's scalars.

4. Session API Reference

The session object is the only interface to the AURA environment.

Data access

df = session.get_dataframe()           # active DataFrame or None
df = session.get_dataframe(copy=True)  # safe copy to modify freely

Modifying data

session.add_variable("newvar", series, label="My new variable")
session.replace_variable("varname", series)
session.drop_variables(["var1", "var2"])
session.drop_observations(mask)        # boolean Series
session.reorder_variables(["id", "year", "wage"])
session.set_dataframe(df)              # replace entire dataset

# Always emit after modifying:
session.events.emit("data_updated", dataframe=session.get_dataframe())

Label access

session.get_var_label("wage")          # "Monthly wage (USD)"
session.get_value_labels("sex")        # {1: "Male", 2: "Female"}
session.label_value("sex", 1)          # "Male"
session.apply_labels(series, "sex")    # labeled Series
session.get_variable_info("wage")      # full metadata dict

Defining labels from a module

session.define_value_labels("yesno", {0: "No", 1: "Yes"})
session.assign_value_labels("employed", "yesno")

Output

# Shortcut — return a string directly:
return "Operation completed."
return tabulate(df, headers="keys")

# Or use the output API:
session.output.add_text("text")
session.output.add_warning("msg")

Events

session.events.emit("data_updated", dataframe=df)   # refresh GUI panels

Result namespaces

session.r    # rclass — general return values
session.e    # eclass — estimation results
session.s    # sclass — string results

session.post_results({"N": 100, "mean": 42.0}, kind="r")
session.get_results(kind="r")

History and survey

session.history      # list of all commands run
session.survey       # dict — survey design metadata

Long commands — progress and interruption

A command that may run for a while should do two things.

Report progress. session.progress_bar(done, total, label) drives the bar in the status bar; passing total <= 0 hides it. It is a no-op when there is no GUI, so the same code runs headless and under test.

Stay interruptible. session.tick() gives the interface a chance to respond and raises BreakError if the user pressed Stop. Call it once per iteration of your outer loop; without it a long loop cannot be interrupted.

for i, rep in enumerate(replications):
    session.tick()                                   # lets Stop work
    session.progress_bar(i + 1, len(replications), "bootstrap")
    ...
session.progress_bar(0, 0)                           # hide it when done

Reporting by group — core/grouping.py

Per-group work in AURA is an option, not a command prefix. The shared helper lives in core/grouping.py and is deliberately free of any command-specific logic, so adding over() to a command is cheap:

from core import grouping

over = grouping.parse_over(parsed)           # None when the option is absent
if over:
    bad = grouping.check_over(df, over, "mycmd")   # unknown grouping variable?
    if bad:
        return bad
    for label, sub in grouping.iter_groups(session, df, over):
        ...                                  # one section per group, ONE table

parse_over(parsed) reads the option off the parsed command and raises ValueError on an unknown sub-option; the sub-options are nolabel, missing and descending. check_over validates the grouping variables against the data. iter_groups(session, df, spec) yields (label, subset) with the ordering and missing-group policy already applied, the label resolved through the value labels — so a command only has to decide how to render each section.

Parse the option outside any broad except. A command that wraps its work in try: ... except Exception: and falls back to a legacy path will swallow the ValueError from a mis-spelled sub-option, and the user gets an ordinary table that looks as if the option had worked. That failure is silent, which is the one kind worth designing against.

5. Result Classes

Declaration

__aura_class__ = "rclass"   # → session.r
__aura_class__ = "eclass"   # → session.e
__aura_class__ = "sclass"   # → session.s

The engine clears the namespace before each call and auto-posts results if run() returns a dict.

Returning output alongside stored results

Use the _output key in the returned dict. The engine extracts it and displays it in the console; the rest goes into the result namespace:

__aura_class__ = "eclass"

def run(session, parsed):
    ...
    return {
        "N":       n,
        "mean1":   mean_a,
        "mean2":   mean_b,
        "diff":    mean_a - mean_b,
        "_output": formatted_table_string,   # displayed in console
    }

Without _output, the dict is posted silently (nothing displayed).

rclass — descriptive commands

__aura_class__ = "rclass"

def run(session, parsed):
    ...
    session.r["N"]    = len(df)
    session.r["mean"] = float(df["wage"].mean())
    return output_string

eclass — estimation commands

__aura_class__ = "eclass"

def run(session, parsed):
    ...
    names = list(result.params.index)

    session.e["N"]      = N
    session.e["r2"]     = result.rsquared
    session.e["names"]  = names                      # the coefficient names
    session.e["b"]      = [float(c) for c in result.params]          # flat list
    session.e["V"]      = [[float(v) for v in row]                   # k x k
                           for row in result.cov_params().to_numpy()]
    session.e["df_r"]   = int(result.df_resid)
    session.e["depvar"] = y_name
    return output_string

The coefficient vector has a fixed shape, and it is not a dictionary. e["b"] is a flat list, e["V"] the matching k×k covariance matrix, and e["names"] the names that index both. Every post-estimation consumer relies on it — nlcom, test, lincom, estimates, bootstrap, and the matrix engine reading matrix b = e(b).

Posting a name-keyed dictionary instead is the one mistake worth guarding against, because nothing rejects it at posting time: the failure surfaces later, inside whichever command tried to use the results, as a type error that mentions neither e(b) nor the shape it wanted. If your library hands you a named series, keep the names in e["names"] and pass the values on as a list.

Post the scalars your estimator is asked about too — e["df_r"] decides whether post-estimation inference uses t or z.

5B. Posting Results — the Return System

§5 covered the result class of a module (__aura_class__ = "rclass" / "eclass"). This section covers how a module posts named results, and how they are read back — the API in core/returns.py. Results are kept in a named archive keyed by recency rather than in a single global slot, so the results of an earlier command survive the next one and stay addressable.

Posting from a module

A handler posts results directly on the session — no helper class required:

def run(session, parsed):
    ...
    session.results.scalar("N", n)
    session.results.scalar("mean", m)
    session.results.string("depvar", y)
    session.results.matrix("stats", arr)          # numpy array
    session.results.table("table", tablespec)     # a TableSpec
    session.results.omatrix("T", omat)            # an OMatrix
    return result(text="…", kind="r")             # r-class | e-class

session.r, session.e, session.s remain plain dicts (kept mirrored for back-compat); post_results(dict, kind) posts a whole dict at once.

The archive

Every command that posts something non-empty is archived under an id built from its canonical name plus a counter: summarize1, summarize2, regress1, … (a svy: prefix yields the id svy). The archive is a bounded deque capped by set nreturn (default 6). One slot is special: last_estimation is protected from eviction, so e(b) / e(V) survive even after several descriptive commands run afterwards.

The lifecycle is driven by execute_text: begin_command_results → run the handler → commit_command_results() (archive iff non-empty; an empty post changes nothing). Ids are monotone and stable — never renumbered — so r(cmd, N) addressing stays valid. clear all / clear results calls returns.reset() (empties the archive and the counters → the next summarize is summarize1 again).

Reading results back

  • In command text — macros.expand_results() substitutes scalar/string r(name) / e(name) / s(name) before parsing (so display r(mean), gen z = r(N)*2, if e(N)>100 all work). e(...) looks in last_estimation first.
  • Direct addressing — r(cmd, name) or r(id, name) reaches a specific archived entry (_lookup_in_entry).
  • Matrices — e(b) / e(V) / r(stats) are left to the matrix engine, which reads them through the archive (matrix b = e(b), matrix C = r(C)).
  • Display — display r(cmd,table) / display r(stats) renders the stored table / matrix.

Named matrices

Matrix row/column names live in MacroState.matrix_names. matrix rownames/colnames A = … sets them; `: rownames A' reads them. They are carried automatically when a matrix is pulled from a posted result (matrix A = r(stats) / e(b) / e(V)), so summarize and regress post their matrices already named.

ereturn / sreturn

ereturn and sreturn are return with flavor e / s; ereturn post b V posts an estimation vector and covariance. A typical estimator posts e(b), e(V), e(names) (+ scalars like e(N), e(df_r)) — which is exactly what makes nlcom, matrix, and bootstrap work on top of it.

Pitfall — silent posts must return [], not None

A builtin handler that posts silently and returns None makes execute() believe the command was not handled → it falls through to the plugin path and raises a bogus r(199) Command '…' unknown. Return an empty list [] for a successful silent post (see commands/return_cmd.py:run_return).

6. Multi-Dataset Modules

AURA provides two mechanisms for modules that need more than one dataset.

6.1 Direct workspace access

def run(session, parsed):
    ws          = session.workspace           # {alias: {"df", "path", ...}}
    active_name = session.workspace_active()  # name of active dataset
    active_df   = session.get_dataframe()     # active DataFrame

    # Access any dataset by alias
    df_1994 = ws["bkf94I"]["df"]
    df_1998 = ws["bkf98I"]["df"]

    # Iterate over all datasets
    for name, snap in ws.items():
        df = snap["df"]
        print(name, len(df))

6.2 The datasrc protocol

For modules that require explicit source declarations with optional variable mappings:

User declares sources:

datasrc 1 "bkf94I.aura", income(revenu) weight(pondh)
datasrc 2 "bkf98I.aura", income(revpc)  weight(pondm)

Module accesses them:

# Load a declared source. It returns a PAIR: the DataFrame copy and the
# source's declaration (its path and the variable roles mapped onto it).
df1, info1 = session.load_datasource("1")
df2, info2 = session.load_datasource("2")

# Resolve a variable name through the mapping
col_income_1 = session.resolve_var("1", "income")   # → "revenu"
col_income_2 = session.resolve_var("2", "income")   # → "revpc"

load_datasource raises ValueError with a clear message if the source was not declared, listing which sources are available.

Comparing two distributions — distset

Beside the two mechanisms above there is a third, for the common case of a command that compares the same variable across two datasets: poverty in 1994 against 1998, one region against another.

distset records the pair once, and the commands then read it:

use "bkf94I.aura"
use "bkf98I.aura"
distset bkf94I bkf98I

A module reads the pairing from session.distset, which is None until one is declared. It also carries whether the two distributions are dependent (paired, sharing a sampling design) or independent, since that decides how the standard error of a difference is computed — a difference command that ignores it will report a plausible and wrong interval.

The advantage over asking for two filenames in the options is that the pairing is declared once and every difference command in a session inherits it.

6.3 The sw protocol — declarative form

The sw (switched-workspace) protocol lets a module accept dynamic option names of the form <role><N>(value) — for example income1(revenu), income2(revpc), weight1(w94), weight2(w98). The role is any name (income, cons, wage, ...); the digit N is a source number; the value inside the parens is a variable name in that source.

To opt in, the module passes sw=True to args(). AURA then:

  • accepts any option matching <role><digit>(...) without complaining about "unknown option";
  • requires the user to terminate the option list with the literal keyword sw;
  • auto-resolves every numbered option against session.datasources (or, by fallback, the N-th workspace dataset) and exposes the result on a.sw.

User syntax:

diff, income1(revenu) income2(revpc) weight1(pondh) weight2(pondm) sw

Module code (canonical):

def run(session, parsed):
    a = args(parsed, session,
        varlist = varlist(min=0, max=0),    # no varlist for sw modules
        sw      = True,                     # enable sw-protocol options
        options = {                         # ordinary (fixed-name) options only
            "level": integer(default=95, min=1, max=99),
        },
    )

    # a.sw is auto-resolved:
    # {"income": [(df1, "revenu", "1"), (df2, "revpc",  "2")],
    #  "weight": [(df1, "pondh",  "1"), (df2, "pondm",  "2")]}
    (df_a, col_a, sid_a), (df_b, col_b, sid_b) = a.sw["income"]

Resolution priority for sw_load(session, sid): 1. session.datasources[sid] — explicit datasrc declaration 2. N-th entry of session.workspace (1-based) — workspace fallback

This means the module works whether or not the user has declared datasrc explicitly. With two datasets in the workspace, sw_load(session, "1") returns the first, sw_load(session, "2") returns the second.

The older pattern that imported sw_resolve from auru._sw and checked parsed.opts.get("sw") manually still works, but it is legacy. Write new sw modules with args(sw=True) only.

6B. Matrices, Macros and Containers

Three engines back the macro/matrix layer. A module rarely calls them directly (it usually emits command lines with run_cmd or reads session.macros), but knowing the surface helps.

Matrices — core/matrix_engine.py

numpy-backed matrix [define] NAME = expr, stored in session.macros.matrices. Operators ' (transpose) * + - :* :/ :^ ^ \ (vstack) , (hstack) A[i,j] (1-based, . = whole dim, a/b ranges). Functions: I J inv invsym rows cols trace det diag cholesky eigenvalues sqrt exp log abs. Bridges: data(varlist [, in(a/b)] [if(cond)]) → filtered columns, and e() / r() / s() → posted results. svmat A [, names()] writes matrix columns to variables; mkmat varlist [, matrix(name)] is the inverse. The classic matrix beta = invsym(X'*X)*X'*y reproduces numpy OLS exactly.

Macros and scalars — core/macros.py

MacroState holds globals, scalars, and a stack of local frames. local / global / scalar define silently; `name' / $name / `=expr' expand. Extended functions `: word count …', `: list uniq …', `: type var', `: variable label var', etc. Temporaries tempvar / tempname / tempfile are cleaned up when their scope pops; tokenize fills the numbered locals `1' `2'. Scalars are visible as bare names in expressions (gen x = _n * k), with a same-named column taking priority.

omatrix — core/omatrix.py

A bi-indexed mixed container (values or strings) wrapping a DataFrame — for transport, not algebra. omatrix NAME = data(varlist) keeps each column's dtype; O', O[rows,cols] select. to_matrix() extracts a numeric block (clear error if a column is non-numeric) so you can cross over to a real matrix. It is the 5th return type (return omatrix T = O; display r(id,T)).

Example: linear fit with confidence band

import numpy as np
import matplotlib.pyplot as plt

def run(session, parsed):
    df    = session.get_dataframe()
    vars_ = parsed.vars
    if len(vars_) < 2:
        return "Syntax: linfit yvar xvar"

    yvar, xvar = vars_[0], vars_[1]
    sub = df[[yvar, xvar]].dropna()
    x   = sub[xvar].to_numpy(dtype=float)
    y   = sub[yvar].to_numpy(dtype=float)

    x_plot = np.linspace(x.min(), x.max(), 200)
    a, b   = np.polyfit(x, y, deg=1)
    y_est  = a * x_plot + b

    n     = len(x)
    s_res = np.sqrt(np.sum((y - (a * x + b)) ** 2) / (n - 2))
    y_err = s_res * np.sqrt(1/n + (x_plot - x.mean())**2 / np.sum((x - x.mean())**2))

    fig, ax = plt.subplots(figsize=(8, 5))
    ax.plot(x_plot, y_est, '-', color='tab:blue', linewidth=2, label='Linear fit')
    ax.fill_between(x_plot, y_est - y_err, y_est + y_err, alpha=0.2, color='tab:blue')
    ax.plot(x, y, 'o', color='tab:brown', markersize=4, alpha=0.6, label='Data')
    ax.set_xlabel(xvar);  ax.set_ylabel(yvar)
    ax.legend();  fig.tight_layout()
    plt.show()

    return f"Linear fit: {yvar} = {a:.4f}·{xvar} + {b:.4f}   (n={n:,})"

7B. Aura Blocks

Inside a .auru module you can switch from Python to AURA syntax with an aura: ... end aura block. This is AURA's in-module escape into command syntax (analogous to a mata: / end block in other packages) — a clean way to use AURA's commands (regress, summarize, twoway, ...) for the statistical and graphical heavy lifting without re-implementing them in Python.

The simple form

def run(session, parsed):

    aura:
        summarize x y
        regress y x, robust
        twoway (rarea ci_low ci_high x) (line yhat x) (scatter y x)
    end aura

    return "Done."

Each non-comment line in the block is parsed by AURA and dispatched through the execution engine — exactly as if you typed it in the console. Comments (//, *, /* */), continuations (///), and #delimit ; all work inside the block.

The bridge form — aura(name=array, ...):

When you have arrays computed in Python (numpy, scipy) that you want AURA to use as columns:

import numpy as np
from scipy import stats

def run(session, parsed):
    df = session.get_dataframe()
    y, x = df["wage"].values, df["age"].values

    # Python: compute the fit and 95% CI
    slope, intercept, *_ = stats.linregress(x, y)
    yhat_np = intercept + slope * x
    se      = np.std(y - yhat_np) * np.sqrt(1/len(x) +
                  (x - x.mean())**2 / np.sum((x - x.mean())**2))
    lb_np   = yhat_np - 1.96 * se
    ub_np   = yhat_np + 1.96 * se

    # AURA: same names, exposed as TEMPORARY columns just for this block
    aura(yhat=yhat_np, lb=lb_np, ub=ub_np):
        twoway (rarea lb ub age, fcolor(navy%20)) ///
               (line yhat age, lcolor(navy)) ///
               (scatter wage age, mcolor(cranberry) msize(small)), ///
               title("Wage by age with 95% CI") ///
               legend(pos(2) size(small)) ///
               graphregion(fcolor(white) margin(medlarge))
    end aura

    return result(text=f"slope = {slope:.4f}", kind="r", slope=slope)

The kwargs yhat, lb, ub become real columns on the dataframe for the duration of the block, then are dropped automatically at end aura.

Scope semantics — what survives

Action inside the block After end aura
gen newvar = ... dropped
replace existing_var = ... persists (mutates a pre-existing column)
aura(x=arr): kwarg injection dropped
permanent newvar directive kept (promoted to permanent)
Exception raised mid-block scope still cleans up (try/finally)
Nested aura: ... end aura refused — a block cannot contain another (see below)

The rule: anything that didn't exist when you entered the block is dropped when you leave it. This keeps test datasets clean and prevents intermediate variables from polluting the user's data browser.

permanent — the escape hatch

When you DO want a computed column to survive:

aura:
    gen logx = log(x)
    gen yhat = a + b*logx
    gen residual = y - yhat
    permanent residual         // ← survives; logx and yhat are dropped
end aura

Python ↔ AURA interpolation

AURA command lines inside the block are emitted as Python f-strings, so {name} placeholders are substituted with Python locals:

def run(session, parsed):
    a = args(parsed, session,
             options={"thresh": real(default=1.96),
                      "k":      integer(default=100)})
    threshold = a.opt.thresh
    k = a.opt.k

    aura:
        keep if x > {threshold}
        gen scaled = x * {k}
        summarize scaled
    end aura

    return "Done."

To put a literal { or } in a command, double it ({{ / }}) — standard f-string rules.

Reading AURA results back in Python

Built-in commands (regress, summarize, ttest, ...) populate session.r, session.e, and session.s. These dictionaries are read normally after end aura:

def run(session, parsed):
    aura:
        regress y x1 x2, robust
    end aura

    names = session.e["names"]          # ['x1', 'x2', '_cons']
    b     = session.e["b"]              # a flat list, aligned with names
    coef  = b[names.index("x1")]
    rsq   = session.e["r2"]
    return result(text=f"coef(x1) = {coef:.4f}, R² = {rsq:.4f}",
                  kind="e", coef_x1=coef, r2=rsq)

An estimator posts its coefficients as the vector e["b"] indexed by e["names"], not as one scalar per regressor — there is no e["coef_x1"] to read. Scalars that stand alone (r2, N, df_r) are posted under their own name, so session.e["r2"] is right.

How it works under the hood

When the execution engine loads a .auru file it pipes the source through core.preprocessor.transform_aura_blocks() before compiling. Each aura: block becomes:

_aura_scope_enter(**kwargs)
try:
    run_cmd(f"command1 vars, opts")
    run_cmd(f"command2 vars, opts")
    ...
finally:
    _aura_scope_exit()

The three helpers run_cmd, _aura_scope_enter, _aura_scope_exit are injected into the module's namespace alongside the existing args, result, outputs, graph, etc. — you don't import them.

_aura_scope_enter snapshots the current column list. _aura_scope_exit diffs the current column list against the snapshot and drops anything new (unless a permanent directive promoted it). The try/finally guarantees cleanup even when an AURA command raises.

Blocks do not nest

A block cannot contain another one. The body of a block is already AURA syntax, so an inner aura: would not be a nested scope — it would be a command, and there is no such command. The preprocessor refuses it and names the line:

line 4: an `aura:` block cannot contain another one. The body of a block is
already AURA syntax, so nesting has no meaning — close the first block with
`end aura` before opening a second, or simply keep all the commands in one
block.

Consecutive blocks are fine, and are the way to interleave Python between two runs of AURA commands:

aura:
    gen outer = x + 1
    summarize outer
end aura

mean = session.r["mean"]          # Python again, between the two blocks

aura(cut=mean):
    keep if x > cut
end aura

Pre-filling a dialog from a command

A dialog that implements preset_from_command(cmd) can be opened already filled in from a command line. This is what lets a help example offer its "open dialog" link, and it is how a reader inspects the arguments of a destructive command before running it.

The method reads a command string and sets the dialog's fields; the contract is a round trip:

dlg.preset_from_command(cmd)
assert dlg.generate_command() == cmd      # what goes in comes back out

Test it that way. A preset that silently drops an option produces a dialog that disagrees with the example printed above it, which is worse than having no preset — the reader trusts the box.

When NOT to use an aura: block

  • Pure numeric work — keep it in numpy/pandas. No need to round-trip through AURA's text parser.
  • Single-line trivial commands — run_cmd("summarize x") directly is just as readable.
  • Conditional logic on AURA output — read session.r / session.e between blocks rather than trying to control flow inside one.

7D. The Estimation Module Pattern

This section describes the standard pattern for writing any estimation command as a .auru module — OLS, logit, probit, poisson, tobit, ivreg, xtreg, etc. All share the same output skeleton; only the numbers and the column conventions differ.

Reference implementation

The canonical example is auru/regress.auru — read it side-by-side with this section. Every estimator should follow the same 8-step flow.

The 8-step flow

"""my_estimator — what it does, syntax."""
__aura_class__ = "eclass"   # or "rclass" / "sclass" / omit

import numpy as np
# any scientific lib you want


def run(session, parsed):

    # 1. PARSE the syntax (manual if you support `i.var` / `c.var` factors,
    #    or via args() / varlist() for plain numeric varlists)
    raw_vars = list(parsed.get("vars", []))
    if len(raw_vars) < 2:
        return error("Syntax: my_estimator depvar indepvars [, options]")
    y_name, x_names = raw_vars[0], raw_vars[1:]
    opts = parsed.opts if hasattr(parsed, "opts") else {}

    # 2. EXPAND factor variables (i.varname) into k-1 indicators
    df = session.get_dataframe()
    all_cols, all_names = [], []
    from core.factor_vars import build_design
    Xdf = build_design(df, x_names)          # k-1 indicators, base level dropped
    all_names = list(Xdf.columns)            # 'size', 'gse:2', 'size#gse:2', ...
    all_cols  = [Xdf[c].to_numpy(float) for c in all_names]
    # build_design drops rows missing on any input; align y to Xdf.index.

    # 3. ESTIMATE — pure Python, your choice of library
    X = np.column_stack(all_cols)
    if not opts.get("noconstant"):
        X = np.column_stack([X, np.ones(len(X))])
        all_names = all_names + ["_cons"]
    y = df[y_name].astype(float).values
    result = my_python_estimator(y, X)

    # 4. ANOVA / fit decomposition (if applicable — skip for ML estimators)
    anova = TableSpec(
        matrix=[[result.ess, k, result.msm],
                [result.ssr, df_r, result.msr],
                [result.tss, df_t, result.mst]],
        rownames=["Model", "Residual", "Total"],
        colnames=["SS", "df", "MS"],
        col_formats=["%.4g", "%d", "%.4g"],
        h_separators={2},
        v_separators={1},
        title=f"My Estimator — depvar: {y_name}",
    )

    # 5. SUMMARY-STATS banner — one call, free format
    stats = build_estimation_header([
        ("Number of obs",   f"{result.n:,}"),
        ("LR chi2(k)",      f"{result.llrt:.2f}"),    # adjust per estimator
        ("Prob > chi2",     f"{result.llrt_p:.4f}"),
        ("Pseudo R²",       f"{result.prsquared:.4f}"),
        ("Log likelihood",  f"{result.llf:.2f}"),
    ])

    # 6. COEFFICIENT TABLE via the generic builder.  Rows for factor levels
    #    use the "group:level_label" naming so build_coefficient_table can
    #    insert section titles and indentation automatically.
    coef_rows = []
    for i, name in enumerate(all_names):
        if isinstance(name, tuple):                  # ("gse", 2)
            var_name, code = name
            lbl = session.label_value(var_name, code)
            level_str = str(lbl) if (lbl != code and isinstance(lbl, str)) else str(code)
            display = f"{var_name}:{level_str}"
        else:
            display = name
        coef_rows.append((
            display,
            float(result.coef[i]),
            float(result.se[i]),
            float(result.tval[i]),                   # or zval for ML
            float(result.pval[i]),
            float(result.ci_lo[i]),
            float(result.ci_hi[i]),
        ))
    coef = build_coefficient_table(
        coef_rows,
        depvar=y_name,
        se_label="Std. err.",                        # or "Robust SE"
        stat_label="t",                              # or "z" for ML
        ci_level=int(opts.get("level", 95)),
    )

    # 7. STORE ECLASS RESULTS (or rclass / sclass per __aura_class__)
    #    b is a FLAT LIST, V the matching k x k matrix, names indexes both —
    #    see "eclass" in section 5. A name-keyed dict here breaks nlcom, test,
    #    lincom, estimates and bootstrap.
    session.e["N"]      = result.n
    session.e["names"]  = all_names
    session.e["b"]      = [float(c) for c in result.coef]
    session.e["V"]      = [[float(v) for v in row] for row in result.vcov]
    session.e["df_r"]   = int(result.df_r)
    session.e["ll"]     = float(result.llf)
    session.e["depvar"] = y_name

    # 7b. HAND THE FITTED MODEL TO POST-ESTIMATION
    #     Without this, `predict`, `margins`, `test` and `lincom` answer
    #     "needs a prior estimation" even though your table printed fine.
    session.set_estimation_model(
        result=fit,                  # the fitted statsmodels Results, if any
        cmd="mycmd",
        depvar=y_name,
        names=all_names,
        b=session.e["b"],
        V=session.e["V"],
        index=Xdf.index,             # rows the estimation actually used
    )

    # 8. RETURN the stacked table — AURA renders it and emits AURAResult(type="table")
    return StackedTable(
        sub_tables=[anova, stats, coef],
        notes=[],                                    # add post-estimation notes here
        shared_column_widths=False,
    )

Shared estimation helpers — core/estimation.py

Do not re-implement the option plumbing every estimator needs. core/estimation.py resolves the conventions once, so all estimators agree:

from core.estimation import resolve_vce, weight_column, fit_kwargs
  • resolve_vce(vce_value, robust=False) turns robust / vce(robust) / vce(hc3) / vce(cluster v) into the covariance choice, so every command spells these the same way;
  • weight_column(parsed, df) resolves the weight clause against the data;
  • fit_kwargs(cov_type, groups=None) assembles what the fitting call needs.

Using them is what makes vce(hc3) behave identically in your module and in the built-in estimators — which is the point of a shared vocabulary.

An estimator that fits a design of its own uses the same helpers for what a library leaves to the caller:

  • collinear_columns(X, weights=None, constant=True, left_to_right=False) gives the columns to leave out; with left_to_right=False they go by the variation left, the rule of regress on plain variables;
  • omitted_note(names) writes the note above the table. Keep an omitted variable in the table and in e(b) and e(V), at 0, so that esttab and _b[x] find it;
  • cov_rank(V) is the rank of a covariance matrix: below the number of coefficients, there is no overall test;
  • set_covariance(result, V, cov_type=None) gives a statsmodels result a covariance computed elsewhere: its standard errors, intervals and tests then read that one.

8B. Debugging and Tracing Tools

Two facilities help while writing scripts and modules: a static linter and execution tracing.

The script linter — core/script_lint.py

lint_script(text) -> [(level, line, msg)] is a pure static analyser (level is "error" / "warning", line is 1-based). The checks are chosen for ~zero false positives (a noisy linter is worse than none):

Level Check
⛔ error unbalanced () / [] / quotes in a command; unbalanced block braces { } over the whole script; an ambiguous abbreviation the engine would reject
⚠ warning an unknown command; an option not allowed by a catalogued command (reuses option_guard.ALLOWED_OPTIONS, with a "Did you mean …?")

It uses the live inventory command_names.COMMANDS (populated by the engine at start-up, so every builtin and scanned auru/* is known), replays the preprocessor's logical-line splitting, exempts control/macro words, and strips the quietly / capture / by: / svy: / bootstrap: prefixes. It never checks whether a variable exists — that is data-dependent.

The same function powers two surfaces:

  • the Script Editor's Problems panel (live, debounced; double-click a row to jump to the line; run-time errors are appended after a Run);
  • Pass 3 of the Module Editor's check_module_source (§8), linting the commands inside aura: blocks.

Execution tracing — set trace

set trace on echoes each command as it runs, with macros expanded, prefixed with - (distinct from the . of a typed command); loop / conditional headers are echoed too, so the program structure is visible. Crucially, the trace is a separate stream, not part of session.output:

session.trace(text)          # writes to session._trace_sink if attached, else no-op
session._trace_sink = sink   # the GUI wires this to a grey "trace" tag in the console

Because the trace never lands in session.output, it does not interfere with the Problems panel's run-time error capture (which diffs session.output).

Setting Session flag Meaning
set trace on/off _cmd_trace Echo each executed command (macros expanded)
set tracedepth N _trace_depth Trace only down to call depth N (module sub-commands count one level deeper, indented)
set tracedeep on/off _trace_errors Full Python traceback on a module error (the old set trace, renamed)

8C. Option Validation — option_guard

An unknown option should be refused, not ignored. AURA enforces this centrally in core/option_guard.py, called from execution_engine.execute() just before dispatch (outside the svy: prefix). It is opt-in: a dict ALLOWED_OPTIONS lists only the commands whose option set is known and faithful to the handler (summarize, tabulate, correlate, ttest, regress, logit/probit/poisson). Commands not catalogued — graphs, fluent-option commands — are never guarded, so there are zero false rejections.

Matching is exact (keys in Command.opts are already lowercased; handlers test exact names). An unknown option raises r(121) Option '…' not allowed with '…' plus a "Did you mean …?" hint; capture / quietly swallow it as usual.

To bring your command under the guard, add an entry to ALLOWED_OPTIONS:

ALLOWED_OPTIONS["mycmd"] = {"detail", "level", "by"}

8D. Fast Numeric Kernels — fastmath

Hot numeric loops can be JIT-compiled with numba, behind a capability flag so AURA still runs (and tests still pass) without numba installed:

from core.fastmath import njit, HAVE_NUMBA   # HAVE_NUMBA → @njit(cache=True), else no-op

@njit
def my_kernel(values, codes):
    ...                                       # pure-numeric body, no pandas

If numba imports, @njit(cache=True) compiles the kernel; otherwise a no-op decorator runs the same body in pure numpy. The first shipped kernel is psu_cov (stratified ultimate-cluster covariance — the hot path of every svy: variance, called B times under bootstrap). Pattern: pre-factorise labels (strata / PSU) into dense integer codes outside numba, keep the kernel purely numeric, and keep a reference numpy oracle (_psu_cov_reference) to assert equality. Measured ×10 on a realistic survey design.

Heavy libraries at first use — core/lazy.py

statsmodels, scipy, matplotlib.pyplot and numba cost about two seconds to import, and most sessions open a dataset long before (or without ever) estimating a model or drawing a figure. AURA therefore imports them at their first use. A module loaded at start-up — the command registry loads nearly all of AURA, and the DAAP shims with it — binds a stand-in at the top and uses it as before:

from core.lazy import LazyModule
sm = LazyModule("statsmodels.api")                  # imported on first sm.<attr>
psu_cov = LazyModule("core.fastmath", "psu_cov")    # imported on first call

Three rules. Use the stand-in only through attribute access or a call — never at import time (_pdf = st.norm.pdf at module level imports scipy at once), and never pass it as a value to the library itself. Every LazyModule target must also be listed in hiddenimports in aura.spec: PyInstaller does not see a module named in a string, and the built application would lack it; tests/test_lazy.py checks both that rule and that import main loads none of these libraries. A .auru module is loaded only when its command first runs, so it may import what it needs at its top as usual.

9. Installing and Distributing Modules

Manual install

%USERPROFILE%\AURA\modules\personal\mycommand.auru

Hot-loaded on every call — no restart needed.

Starting a package

pkg new writes a working skeleton. It is the quickest way to get the manifest right, since it generates one:

pkg new mystats, author("A. Araar") description("Demo tools") parent("C:/repo")

It creates a directory named after the package:

C:/repo/mystats/
    mystats.lst      the manifest
    mystats.auru     a module stub
    mystats.aurh     its help page
    mystats.demo     a demo stub
    README.md

The manifest — <name>.lst

The manifest is a list of tagged records: a one-letter tag, a space, then the value. Blank lines and lines opening with # are ignored. This is exactly what the command above produced:

v 0.1
d Demo tools
d Created on 2026-07-20 by AURA pkg new
a A. Araar
f mystats.auru
f mystats.aurh
f mystats.demo
f README.md
Tag Meaning
v Version. pkg check and pkg update compare it numerically, so 1.10 is newer than 1.9
d Description. Repeatable — write one line per paragraph
a Author
r Required third-party Python libraries, space-separated. Repeatable
f A file to install. Repeatable

The f records are what make a package: only the files listed there are installed, and a manifest without one stops the install with "has no files listed". A file is fetched relative to wherever the manifest was found, and a path containing .. is rejected.

Declaring dependencies with r lets a user resolve them before running anything:

r scikit-learn

pkg check-deps mystats        report what the package needs and what is missing
pkg install-deps mystats      install the missing ones

In the frozen installer this is source-only. The packaged AURA has no pip, so pkg install-deps is a no-op, and only the libraries AURA bundles — pandas, NumPy, SciPy, statsmodels, matplotlib, Plotly — are importable. A package that needs an unbundled library (e.g. scikit-learn) therefore runs only from a source install, or with that library added at build time. For packages you distribute to installer users, prefer the bundled stack.

The repository index — aura.cnt

A repository is a directory or a URL holding an aura.cnt index beside the packages. Same tagged-record grammar:

v 1.0
d Demo repository
p mystats  Demo tools

p declares one package — its name, then a description. pkg dir reads this file, so a package absent from aura.cnt is not listed, although it can still be installed by name. Note that pkg new does not write aura.cnt: it builds one package, while the index describes the collection, so you maintain it.

Two layouts are supported. A package is looked up in this order:

<repo>/mystats/mystats.lst      per-package subdirectory — what `pkg new` builds
<repo>/mystats.lst              flat

Package commands

pkg new <name> [, author("...") description("...") parent("dir")]
pkg from <URL|path>                   point at a repository
pkg dir [from <URL|path>]             list the packages it offers
pkg describe <name>                   read a manifest before installing
pkg install <name> [from <URL|path>] [, replace]
pkg list                              what is installed
pkg check                             which installed packages have a newer version
pkg update <name|_all>
pkg check-deps <name>  /  pkg install-deps <name>
pkg enable <name>  /  pkg disable <name>       show or hide its menu
pkg uninstall <name>

A full cycle against a local directory, which is also how to rehearse a release before publishing it:

pkg from "C:/repo"
pkg dir
pkg describe mystats
pkg install mystats
pkg list

Packages install under %USERPROFILE%\AURA\modules\plus\<name>\, which is on the search path, so their commands work immediately — no restart.

Adding menu entries

A package that ships an aurap.menu file at its root gets menu entries built at start-up. The file is a manifest, and AURA reads it: no package code is imported or executed to build a menu, so a broken entry cannot stop the application from starting.

package: mystats
author:  A. Araar
version: 0.1

submenu Statistics > &My Stats
item My Stats > "Summary curve" : dialog mystats

Entries may go under User (a first-level menu reserved for packages, one submenu per package) or be injected into Data, Statistics, Graphics or Tools beneath a submenu named after the package. An item's action is dialog <cmd>, command <cmd> or help <cmd>; & marks the keyboard accelerator. Injection only ever adds — a package cannot replace or remove a built-in entry.

Example 1 — Mean with confidence interval (rclass)

import numpy as np
from scipy import stats
from tabulate import tabulate
from core.syntax import syntax, integer, varlist

__aura_class__ = "rclass"


def run(session, parsed):
    syn = syntax(parsed, session,
        varlist_spec = varlist(min=1, numeric=True),
        options      = {"level": integer(95, min=1, max=99)},
    )
    df    = syn.df
    level = syn.opt.level
    alpha = 1 - level / 100

    rows = []
    for var in syn.varlist:
        s  = df[var].dropna()
        n  = len(s)
        m  = float(s.mean())
        se = float(s.sem())
        ci = stats.t.interval(1 - alpha, df=n - 1, loc=m, scale=se)
        rows.append([var, n, round(m, 4), round(se, 4),
                     f"[{ci[0]:.4f}, {ci[1]:.4f}]"])

    session.r["N"]    = len(df)
    session.r["mean"] = rows[0][2] if rows else None

    return tabulate(rows,
        headers=["Variable", "N", "Mean", "Std. Err.", f"[{level}% CI]"],
        tablefmt="simple")

Example 2 — Mean comparison across two datasets (eclass, sw protocol)

The module built here, diff, is an example shipped as examples/modules/diff.auru — not a registered command (that role is filled by DAAP's dimean). Read it alongside the code below, or drop it on your adopath to run it.

import numpy as np
from auru._sw import sw_resolve

__aura_class__ = "eclass"


def _wmean(series, weights=None):
    x = series.dropna().to_numpy(dtype=float)
    if len(x) == 0:
        return float("nan"), 0
    if weights is not None:
        w = np.asarray(weights, dtype=float)[:len(x)]
        return float(np.sum(x * (w / w.sum()))), len(x)
    return float(np.mean(x)), len(x)


def run(session, parsed):
    if not parsed.opts.get("sw"):
        return "Error: option 'sw' required.\nSyntax: diff, income1(var) income2(var) sw"

    try:
        sources = sw_resolve(session, parsed.opts)
    except ValueError as e:
        return f"Error: {e}"

    role = next((r for r, e in sources.items() if r != "weight" and len(e) >= 2), None)
    if role is None:
        return "Error: need two numbered options, e.g. income1(var) income2(var)"

    df_a, col_a, sid_a = sources[role][0]
    df_b, col_b, sid_b = sources[role][1]

    w_a = w_b = None
    for df_w, col_w, sid_w in sources.get("weight", []):
        if sid_w == sid_a:   w_a = df_w[col_w].to_numpy(dtype=float)
        elif sid_w == sid_b: w_b = df_w[col_w].to_numpy(dtype=float)

    mean_a, n_a = _wmean(df_a[col_a], w_a)
    mean_b, n_b = _wmean(df_b[col_b], w_b)
    diff         = mean_a - mean_b
    pct          = diff / mean_b * 100 if mean_b != 0 else float("nan")

    sep = "-" * 56
    out = "\n".join([
        sep,
        f"  Mean comparison ({role})",
        sep,
        f"  src {sid_a}  {col_a:<18}  N={n_a:>8,}   mean={mean_a:>16,.4f}",
        f"  src {sid_b}  {col_b:<18}  N={n_b:>8,}   mean={mean_b:>16,.4f}",
        sep,
        f"  Diff (src{sid_a} - src{sid_b})       {diff:>16,.4f}",
        f"  % change                       {pct:>15.2f}%",
        sep,
    ])

    return {"meanA": mean_a, "meanB": mean_b, "diff": diff, "pct": pct,
            "nA": n_a, "nB": n_b, "_output": out}

Example 3 — Standalone figure (no data required)

import numpy as np
import matplotlib.pyplot as plt


def run(session, parsed):
    x = np.linspace(0, 10, 11)
    y = [3.9, 4.4, 10.8, 10.3, 11.2, 13.1, 14.1, 9.9, 13.9, 15.1, 12.5]

    a, b  = np.polyfit(x, y, deg=1)
    y_est = a * x + b
    y_err = x.std() * np.sqrt(1/len(x) +
                               (x - x.mean())**2 / np.sum((x - x.mean())**2))

    fig, ax = plt.subplots()

    ax.fill_between(x, y_est - y_err, y_est + y_err, alpha=0.2)
    ax.plot(x, y, 'o', color='tab:brown')
    ax.set_title("Linear fit with confidence band")
    fig.tight_layout()
    plt.show()

12. The auru.connect API (reference)

The injected helpers documented throughout this guide come from the auru.connect package. That is the stable public API for third-party module developers. core.* modules (core.syntax, core.errors, core.output) are AURA internals and may evolve.

The execution engine injects the following names into every .auru namespace before executing it.

Inputs (from auru.connect.inputs)

Validators and accessors for command arguments:

  • args — the main declarative entry point; validates everything
  • varlist — declare a variable list (min/max, numeric, factor, etc.)
  • flag, integer, real, string — option type declarations
  • varname — single variable name (must exist in active dataset)
  • choice — string option restricted to a given set of values
  • active_df — the active pandas DataFrame
  • sw_pair, sw_load, sw_resolve — multi-dataset (sw protocol) helpers
  • inputs — the namespace itself, for explicit inputs.args(...) style

Outputs (from auru.connect.outputs)

Result producers — wrap return values into AURAResult objects:

  • result — store and emit a structured result
  • text — plain-text message
  • warning — emit a warning (yellow in console)
  • error — emit an error (red, stops the command)
  • note — emit a discreet informational note
  • outputs — the namespace itself

Graph (from auru.connect.graph)

  • graph — graph option translator (single namespace)

Writing a graph module

For graph commands, use graph (the third connector). It translates the whole graph-option vocabulary (lcolor, lpattern, lwidth, mcolor, msymbol, msize, fcolor, fintensity, legend(pos(N)), title(), xtitle(), ...) into matplotlib kwargs.

"""myplot — Custom scatter with the standard graph options."""
import matplotlib.pyplot as plt

def run(session, parsed):
    a = args(parsed, session,
        varlist = varlist(min=2, max=2, numeric=True),
        options = graph.standard_options(),   # the whole option vocabulary
    )

    y_var, x_var = a.varlist[0], a.varlist[1]
    fig, ax = plt.subplots(figsize=(8, 5))
    ax.scatter(a.df[x_var], a.df[y_var],
               label=y_var,
               **graph.scatter_kwargs(vars(a.opt)))
    graph.apply_all(ax, vars(a.opt))        # titles + axes + legend
    plt.show()
    return text(f"Plotted {y_var} against {x_var}.")

Note the vars(). The option namespace a.opt is convenient in Python — a.opt.mcolor — but the connector looks its options up by key, so hand it the underlying dictionary. Passing the namespace itself fails on the first plotted point with 'SimpleNamespace' object has no attribute 'get'.

Your module now accepts myplot y x, mcolor(navy) msymbol(Oh) title("…") legend(pos(6)) — the same option vocabulary as any built-in graph command.

So you can write args(...), result(...), etc. directly — no import. Optional explicit form for IDE autocomplete:

from auru.connect import inputs, outputs   # optional; both styles run identically

def run(session, parsed):
    a = inputs.args(parsed, session, varlist=inputs.varlist(min=1))
    return outputs.result(text="...", N=10)

A working tutorial module is included — see auru/histo.auru and its help file auru/histo.aurh.

13. Writing a Help File (.aurh)

Every .auru module can ship an optional .aurh file (same name, same directory).
When present, help <module> opens a formatted HelpWindow instead of printing the docstring in the console.

Quickest start — scaffold one from the Module Editor

Open your module in the Module Editor (Tools → Module Editor) and pick Module → Generate .aurh help, or the help button on its toolbar. It writes <module>.aurh beside the module, pre-filled with the sections in order and an inline cheat-sheet of every tag, so there is nothing to look up while you fill it in.

Why a dedicated mini-format instead of Markdown ?

The .aurh syntax is intentionally simpler than Markdown :

.aurh What it gives Why not Markdown
# Title Blue title bar (one line) Markdown # would just be a heading
##section Predefined named section (description, syntax, options, …) Avoid every author inventing their own headings
{cmd:txt} Bold blue mono (commands) Markdown has no semantic command color
{opt:txt} Bold dark-blue mono (options) Idem
{it:txt} Italic grey (metavariables) Markdown *x* is only italic, no color
{res:txt} Green mono (r(...) stored results) Idem
{help:name} Clickable in-app link to another help Markdown links would need to know AURA's resolver
{url:label\|http://} Clickable browser link Markdown allows it but our format keeps the same { } rhythm

Result: consistency across all module help pages, no CSS, no HTML, no surprises.

The HelpWindow viewer is separate from the new TabbedViewer/Markdown renderer — .aurh always opens in HelpWindow, .md always in TabbedViewer.

File structure

# ModuleName — Short description          (title bar)

##description
Free text. Inline tags supported.

##syntax
{cmd:command} {it:varname} , {opt:option}({it:value}) [{opt:flag}]

##options
{opt:option(value)}   What it does (default X)
{opt:flag}            Boolean; present means True

##examples
. command varname, option(value)
. command varname, option(value) flag

##stored_results
{res:r(name)}    Description of stored scalar

##remarks
Additional notes. Cross-references: {help:ttest}

##author
Your name — Module v1.0

Lines inside ##examples that start with . are rendered as command-prompt lines (monospace, light background). All other lines accept inline tags.

##exampledata — make the examples runnable

A help page can carry the data its own examples need. Add an ##exampledata section holding ordinary AURA commands, and every . line under ##examples becomes clickable: the reader gets a run in command window link, and a open dialog link for commands whose dialog can pre-fill itself.

##examples
    Every numeric variable at once
. summarize
    One variable in detail
. summarize wage, detail

##exampledata
clear
set obs 200
gen wage = 20000 + rnormal(0, 4000)
gen educ = 8 + int(runiform()*10)

The setup commands are run, never displayed — they exist so the example has something to work on. Clicking a link puts the reader in demo mode: their own data is set aside rather than overwritten, and demo end restores it. That matters most for commands that replace the data, since the reader can look at the sample before transforming it.

The section is also the switch. A page without ##exampledata shows its examples as plain text, because a link that ran against whatever the reader happened to have loaded would be worse than no link at all.

Two ways to supply the data, and the choice is worth making deliberately:

  • Generate it with set obs + gen, as above. The page is then self-contained and cannot break.
  • Ship a file, loaded with use "data/<file>". Sample data must live inside AURA — auru/data/ or auru/demo_data/ — never at an absolute path on the author's machine, which would fail for every other reader and would not survive packaging.

Examples that build on each other. A click reloads the page's data, so an example cannot count on what an earlier click did. Consecutive example lines form a group instead: a click first replays, silently, the examples above the clicked one in its group. Write an example that needs the one above it (predict after logit, restore after preserve) directly under it, and separate independent variants with a blank line or a line of text, which starts a new group. The rules live in core/help_examples.py:

  • the replay never runs a command that touches files or the system, opens a window, or runs code AURA cannot inspect (save, export, use, erase, cd, shell, log, help, db, browse, graph save, a py: block…, or any command with an option that writes a file: export(), xls(), saving()); such a command runs only when it is the one clicked;
  • a block — py: … end py, or forvalues … { … } — is one example, run as a whole, with its links under its last line;
  • an example line holds one command: no trailing // comment and no explanation on the same line (put it on the line above).

##technote — the method behind the command

For a command whose defensible details matter — an estimator, a variance formula, a bandwidth rule — ##technote holds the technical note: what is computed, and under which convention. It keeps the method out of ##description, which should stay short enough to answer "what is this for".

14. Writing a Demo

A demo is a small directory shipped with AURA (or with a .auru module) that walks a user through a concept in a few minutes. The AURA shell takes care of the lifecycle — you only write three short files.

Quickest start — scaffold one in 2 seconds

. demo template mycmd
demo template: created C:\…\demo\mycmd
  Edit manifest.json, the .aur script, and add your dataset.
  Test with:  demo start mycmd

The scaffold gives you a working demo (with a tiny placeholder CSV). Replace the data, edit the script, refine the manifest — and you are done.

Directory layout

demo/<name>/
  manifest.json        ← REQUIRED — metadata
  <name>_data.csv      ← REQUIRED — at least one dataset (CSV or .aura)
  <name>_script.aur    ← REQUIRED — at least one .aur script
  README.md            ← OPTIONAL — pedagogical detail, shown via the banner

Manifest schema (manifest.json)

{
  "title":             "My demo — short subtitle",
  "one_liner":         "What the user will learn in 1 sentence.",
  "level":             "beginner",
  "datasets":          ["mycmd_data.csv"],
  "scripts":           ["mycmd_script.aur"],
  "auto_load":         true,
  "auto_open_script":  true,
  "auto_run":          false,
  "estimated_time_min": 5
}
Field Required Description

one_liner recommended Shown in demo list and the banner

estimated_time_min optional Shown to set expectations

Single-file demos — @demo front-matter

For a simple demo (one dataset, one script) the manifest.json is overkill. Instead, put a * @demo front-matter block at the top of the .aur script — the whole demo is then a single file:

* @demo
* @title:    Tabulate basic — Frequencies and cross-tabs
* @level:    beginner
* @data:     tab_data.csv
* @oneliner: One-way, two-way and chi-squared frequencies in 3 minutes.
* @related:  tabulate, tab1, tab2
* @time:     3

* ─── Step 1 — One-way frequency ───────────────────────────────────
tabulate region
...

Recognised directives: @demo (required marker), @title, @level, @data (comma-separated), @scripts (defaults to the file itself), @oneliner, @related, @time.

Resolution rule: if a manifest.json exists in the demo directory it wins; otherwise the scanner reads the @demo front-matter of the first .aur file it finds. The two forms are fully interchangeable.

Where demos are discovered

The scanner walks (in order) :

  1. <project>/demo/<name>/ — official AURA tutorials
  2. ~/AURA/demo/<name>/ — your personal demos
  3. <project>/auru/<module>.demos/<name>/ — bundled with a .auru module
  4. ~/AURA/modules/personal/<module>.demos/<name>/
  5. ~/AURA/modules/plus/<pkg>/<module>.demos/<name>/
  6. ~/AURA/modules/base/<module>.demos/<name>/

Each demo is grouped by source (built-in, personal, module name, …) and runs from a command's help page or the demo command.

Bundling a demo with your .auru module

If you ship a module named mycmd.auru, place demos next to it under mycmd.demos/:

auru/
  mycmd.auru
  mycmd.aurh
  mycmd.demos/
    basic/
      manifest.json
      basic_data.csv
      basic_script.aur
    advanced/
      manifest.json
      advanced_data.csv
      advanced_script.aur

When a user installs your package via pkg, all of mycmd.aurh + mycmd.demos/ install together, and the demos become available under the mycmd group.

Writing a good demo script

A demo script (.aur) is plain AURA code with step markers as comments:

* ════════════════════════════════════════════════════════════════════
*  Demo: My command
*  Level: beginner    ·    Estimated time: 5 minutes
*
*  What you will learn:
*    - bullet 1
*    - bullet 2
* ════════════════════════════════════════════════════════════════════

* ─── Step 1 — One-line description ─────────────────────────────────
describe
summarize

* ─── Step 2 — Try something simple ─────────────────────────────────
mycmd y x

* ─── Step 3 — Restrict the sample ──────────────────────────────────
mycmd y x if region == 1

The user selects a step (one or several lines) and presses F8 (Run selected). They learn by doing — not by watching.

Safety contract

The demo runtime guarantees that end restores:

  • The full workspace (datasets + active alias)
  • The current working directory
  • r(), e(), s() results dictionaries

So the user can experiment freely inside a demo — clear, drop, replace_active, anything — knowing one click brings everything back.

Per-command demos — the .demo protocol

Alongside the name-guided system above, core/demo_file.py is a lighter layer: ship a numbered demo file auru/<cmd>.demo next to a module's .auru / .aurh. Format: #demo N | title opens a demo, * … lines are narration, other lines are AURA commands.

#demo 1 | OLS with a factor variable
*  Regress wages on schooling and a region factor.
use wages.csv
regress wage educ i.region

Data resolves per-command first (auru/<cmd>.demos/) then from a shared pool (auru/demo_data/); a self-contained demo can also build its data with set obs + gen. Commands: demo <cmd> list, demo <cmd>, number(#) (replays: echoes . cmd + results), with options interactive (materialises a temporary script in the editor) and keep (copies the demo's final dataset into the session). The inline replay runs in a disposable sandbox Session/Engine, so the real session (data, r/e/s, macros, settings) is never touched. Demos run from a command's help page or the demo command. Example: auru/regress.demo.

15. AURADB — the Dialog Studio

AURADB (auradb/) is a declarative mini-language for describing a dialog box → parsed into a spec → rendered with a Tk auto-layout engine → and used to generate the AURA command line. It is an authoring tool: AURA never executes through it — the point is to produce the right syntax fast. Launch it from Tools → Dialog Studio in AURA, or standalone with python -m auradb.studio <file.auradb>.

The language

No pixel coordinates: you declare widgets and the engine lays them out. Decoupled components parser.py → spec.py → (command.py, dialog.py).

  • Widgets — TEXT, EDIT, VARLIST, VARNAME, FILE, CHOICE (combo/radio/listbox), SPIN, CHECK, TEXTBOX, COLOR, EXPR, GROUP, plus the composite VARSELECT (the regress-style continuous/factor selector) and MATRIX (a grid of inputs).
  • Command emission — EMIT "{}" feeds a widget's value into the command; the assembler command.py builds [by v:] cmd <positionals> [if][in] [weight] [, options].
  • Declarative reactions — SHOW / ENABLE <widget> WHEN <cond> with compound AND / OR / NOT; a hidden widget never leaks into the command.
  • Layout divisions — ROWS(...) / COLS(...) give a CSS-grid of cells (R1 / C2, nestable) addressed relative to the cell; TAB "name" creates notebook pages. FILL / LINE colour any component, cell, or group.

The full grammar is in auradb/SPEC.md; examples live in auradb/examples/ (regress_full.auradb reproduces the regression dialog).

The Studio

auradb/studio.py is the unified tool: Code (a .auradb text editor with a Problems panel and live auradb/lint.py diagnostics), GUI (the visual editor auradb/editor.py — drag / resize / recolour on the same spec object), and Preview (the runtime dialog embedded). One spec, three views, kept in sync; Save writes the .auradb text (comments preserved).

Testing rule

For independent AURADB development, run only tests/test_auradb.py — not the full suite.

16. The Graph Object Model (.aurg)

A .aurg is a saved, editable AURA graph. The model is deliberately small and its guiding rule is that a reopened graph is self-contained: it carries its own frozen data and is edited without ever touching the live workspace.

The spec — core/graph_spec.py

GraphSpec is a light dataclass tree with a lossless JSON round-trip (GraphSpec.from_dict(spec.to_dict()) == spec). It has two coexisting forms:

  • recipe — source_command (the AURA command that drew it) + data (the referenced columns, frozen). Reopening re-runs the command over the frozen data → an identical figure. This is the universal, lossless path.
  • structured — a list of Marks (one per plotted series) plus the shared blocks xaxis / yaxis / y2axis (AxisSpec), legend (LegendSpec), titles (TitleSpec) and overall (OverallSpec, incl. scheme / palette). A Mark composes the reusable MarkerStyle / LineStyle / FillStyle blocks — the same homomorphism the GraphBuilder encodes.

Saving and rendering

  • The graphs of a session — each 2-D graph drawn is an AuraGraph in session.graphs (core/graphs.py): its command, a copy of the columns it references, frozen at draw time (graph_capture.freeze_recipe), its edited GraphSpec, the place and size of its window, and a mode — view (its graph window) or edit (its editor). graph_capture.adopt_figure(session, fig, command, data) makes a drawn figure the window of such a graph: it titles the window Graph N — command, adds the Start Graph Editor button when the catalogue knows an editor for the type, and drops the graph when the window is closed for good. The engine, graph mpl, graph use and the end of an edit call it.
  • Edit and back — the button closes the graph window and opens the editor at its place (main._edit_graph); closing the editor redraws the edited spec with commands/graph_io.draw_spec (marks through the renderer; a recipe by re-running its command, with the editor's common options, on its frozen data) in a window at the same place and size (main._end_edit).
  • Saving — graph save and the toolbar disk icon (.aurg is its default format) write graph.current_spec(): the graph as it stands, edits included.
  • Structured export — modules/graph_export.spec_from_plots() turns GraphBuilder state into marks; spec_from_command_string() parses a command into marks so a recipe can open object-by-object.
  • Rendering — modules/graph_render.render(spec, ax) draws onto a bare Figure, reusing the engine's vocabulary and, for computed types (pie / histogram / bar), delegating to the engine drawer so the object never diverges from the live command.

The catalogue — core/graph_catalog.py

One GraphType descriptor per 2-D type: {family, positional, has_axes, computed, part_to_whole, editor, is_mark, overlay_plots}. It is the single source of truth for dispatch and, above all, for how a saved graph reopens: editor_for_spec(spec) returns the target editor, which main.open_graph uses.

Adding a new graph type = one catalogue entry + one drawer. Everything else — command registration, the reopen editor, help — follows from the descriptor.

The editors

editor in the descriptor is one of: object (the multi-mark gui/graph_editor.py, for twoway/scatter/line/…), dedicated (a per-type window: gui/pie_editor.py, gui/histogram_editor.py, gui/bar_editor.py, and gui/curve_editor.py for kdensity/cdfplot; they share their frame — menu, preview, Titles/Style tabs, file operations — in gui/recipe_editor.py, and work on the graph object core/graph_object.py (graph → plots → curves, with its legend): each control is bound to its part of the tree with _bind_control(var, read, write), the command is the one the editor opened with, changed only where a control was changed, and per-curve edits follow Curve.ident — what the curve draws, not its place), recipe (read-only preview, e.g. the 2-axes barofpie). Every editor is built on the spec's frozen data via a private DataManager — never the workspace. The dedicated editors share one layout (a fixed window; Panel A = data + a tabbed option notebook; Panel B = a live preview drawn by the engine drawer) and save back to .aurg. help graph is the user-facing counterpart.

17. AI-Assisted Module Authoring

AURA can generate a new command — a .auru module with its .aurh help, optional .auradb dialog and tests — with a large language model. The subsystem is core/ai/: provider-agnostic, dependency-free (raw urllib, no SDK), and opt-in (no network until the developer enables it).

Providers — core/ai/provider.py, config.py

One tiny interface: generate(system, user) -> text. Three backends: anthropic (Claude, the Messages API), openai (any OpenAI-compatible endpoint — cloud or a local Ollama / LM Studio), and fake (deterministic, offline, for tests). make_provider(config) builds one from the saved config. Gemini / OpenAI / Groq / Cerebras / OpenRouter / Mistral / Ollama all ride the single OpenAI-compatible backend — only the Base URL + model differ. Config is ~/AURA/config/ai.json (core/ai/config.py; is_ready() gates on enabled + a key for cloud / a base_url for local). Tools → AI Settings (gui/ai_settings_dialog.py) edits it — a preset fills the Base URL + a default model, all editable. (Hosts behind Cloudflare need a browser-like User-Agent; the provider sets one.)

The project scaffold — core/ai/project.py

A module is written inside a project — a working folder carrying AURA's rules and the developer's material, so AURA-IA and an external agent (Cursor, Claude Code…) can share it. create_project(name, location) (Tools → New Module Project) makes docs/ (AURA's authoring/AUTHORING_*.md master files copied in), refs/ (reference material), out/ (the produced files), data/ (small datasets, referenced by a relative path), plus project.json and an AGENTS.md pointing an external agent at docs/. The user types only a name and a location.

Generating and shipping — chat.py / generator.py, Produce Package

The Module Editor's chat (core/ai/chat.py, generator.py) generates and revises the module grounded on the live master files (never a stale copy), and the produced .auru runs in the session for immediate testing. Produce Package (gui/produce_package_dialog.py → core/package_build.build_package) turns a finished project into an installable package (a .lst manifest + the files), optionally with a menu entry, and can pkg install it.

Validating — the headless test service and the two gates

Whoever drafts (AURA-IA or an external agent), the validation is one shared service — never forked. core/ai/test_service.py runs a module HEADLESS in an isolated throwaway session (the developer's workspace is untouched) and returns AI-legible JSON: {ok, errors[], notes[], output[], graphs[], values{r,e,s}}. It is built on the existing sandbox (ExecutionEngine.test_module_source), so it exercises real AURA code, not a copy.

The loop runs against two gates:

  • Gate 1 — it RUNS. No syntax / Python error → ok:true. Each error carries the offending line, with AURA's internal frames and absolute paths stripped.
  • Gate 2 — the NUMBERS are right. The module's own tests/test_<cmd>.py encode the target from refs/ (a reference output, a paper's table) as numeric assertions; the service runs them without pytest (installable-safe, no second-pytest deadlock) and reports pass/fail per case with the failing line. ok:true is necessary but not sufficient — the tests are the target.

The internal loop wires both gates together (validate.py:validate_bundle(..., run_tests=True) → chat.respond / generator.generate_with_fixes re-prompt the model until both are green). The external door is a project's AGENTS.md, which bakes a from-anywhere launcher (aura-test → tools/aura_test.py, self-bootstrapping sys.path; the aura-test.cmd wrapper runs AURA's own venv Python) so an agent like Claude Code or Gemini self-checks and iterates to ok:true + tests.failed == 0. Both orchestrators therefore honour the same contract and the same ground truth.

The authoring rules the model is grounded on — the command contract, the help / dialog / test formats, the survey SE engine, the conventions — live in core/ai/authoring/ and are exactly the files copied into a project's docs/.
